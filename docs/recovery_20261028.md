## Fix and resumption contract

`backup_storage.py` establishes CFS staging/cache paths inside the backup worker,
even with no inherited caller environment. `hf_sync.py` rejects >=1GiB root-disk
snapshots and checks space before copying. Monitoring now records disk space
and inodes, as well as cgroup/GPU statistics. The real tmux backup path must
verify the 1k checkpoint in HF before the training chain proceeds.

`sft_ovmm.py --storage-map` allows only checked changes to four storage paths.
The original frozen config hash is retained, and rank/world/step/optimizer/RNG/
sampler checks are unchanged. Migration cannot change the seed, loss or budget.
`--validate-resume` runs the existing validation loader before the first resumed
optimizer update, to exercise the exact failure path. Saved RNG is restored
after that check. New run logs retain records through step1000; later records
from the failed attempt are preserved separately in `incident/`.

`recovered_resume_chain.py` waits for hash-verified data/checkpoint restoration,
inherited data gates and HF receipt, regression tests, a clean-tmux staging
test, the actual periodic uploader's 1k HF receipt, free GPUs and disk headroom.
Only then does it resume from 1000 to the original 10000-step horizon.
No new collection, M-SFT, RL, FP4 or architecture changes are authorized here.
Evaluation remains PA-OG + Base Lock with the frozen observable switches.

The W&B recovery attempt uses a new run ID linked to the crashed parent rather
than hiding the rollback from step2000 to step1000.
